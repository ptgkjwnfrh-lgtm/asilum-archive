## Corrections to the previous instructions

Three things the old STEP 1 asserted that turned out to be wrong or unusable.
They cost real time; do not repeat them.

1. **`mail.send` is NOT the success signal under custom SMTP.** The old text
   said to verify by finding `"event":"mail.send"` with
   `"mail_from":"asilum@asilummagazine.com"`. That event appears only when
   Supabase's *shared* sender handles delivery. With custom SMTP the handoff
   goes to SendGrid and no such line is emitted. **The real signal is the
   absence of the `535`** — a `/recover` returning `200` with no `error` field.
2. **The Supabase settings page cannot confirm a save.** The password field
   renders blank after a cold reload by design ("cannot be viewed once saved"),
   so a blank field is not evidence either way. What *does* prove a save landed
   is a `"reloading api with new configuration"` line in the auth logs.
3. **The middle segment of an `SG.` key is its key ID**, and SendGrid displays
   that ID permanently on the API Keys page. That lets you check whether the
   stored password is the live key — reveal it, compare that segment — without
   the secret ever needing to leave the page.

## ⚠️ A PRODUCTION DATA CHANGE WAS APPLIED — read this before touching gamma

**The gamma bridge was inert and is now alive.** All 2,632 live edges sat at
`contributors = 0`, so `edgeStrength()` returned 0 and `getEdges` answered every
anchor with **nothing**. `/stats` reported "graph edges 2632", which reads as a
healthy graph, and that was the only number anyone could see.

This was **deliberate**: `schema-v22` refuses to grandfather historical rows,
because inferring `contributors` from `w` would fabricate history and — since
the poisoning attack inflates `w` — would hand the highest trust to the
most-likely-poisoned edges. It waited for organic corroboration that never came:
since v22 landed on Aug 5, production has recorded **1 favourite**, and a pair
needs two positives from one identity.

The owner first asked to set `BRAIN_EDGE_CORROBORATION=0`. **That flag is a
security control, not a tuning knob** — `scripts/measure-graph-corroboration.mjs`
measured a forged item at **rank 37 of a victim's 60-slot page** under the legacy
rule and **absent** under corroboration. Once that was surfaced the owner chose
the backfill instead. **The flag was never changed and is still enabled.**

`scripts/backfill-edge-contributors.mjs` rebuilt the ledger from `user_events` —
the same evidence the live path writes from, **not** from `w`, so v22's objection
stands. It mirrors `app/api/interaction/route.js` exactly: positive actions at
the live weights (bag 2 / share 1.5 / save 1 / favorite 1), each paired with that
identity's `CO_ENGAGE_SPAN` most recent distinct prior positives, both endpoints
catalog-validated (the r17 guard against global `reading:<id>` pseudo-anchors),
`CONTRIB_CAP` per pair, and **only pairs that already exist** — it cannot invent
an edge.

## Refuted — recorded so it is not re-tried

**The two-sided `OR` in `getEdges` is not a missing-index defect.** The plan
really does `BitmapOr` both v22 indexes and then Sort, discarding the ordering
those indexes exist to provide, and a `UNION ALL` rewrite measured 16.8 ms →
3.7 ms. **That measurement was wrong** — the `OR` ran cold and the `UNION` ran
warm. Warmed and repeated across three anchor sets the shipped `OR` wins every
time (4.50 vs 6.68, 2.58 vs 3.62, 2.88 vs 4.49 ms). At 2,632 rows the sort is
cheaper than doubling the index descent.

## Traps learned this session (all cost real time)

1. **Benchmark cold vs warm and you will invent a finding.** The `getEdges`
   "4.5× win" above was entirely a cache artefact. Always warm both shapes, run
   each ≥3 times, and compare medians — and prefer `EXPLAIN (ANALYZE)` execution
   time, which excludes network noise, over wall clock to a remote database.
2. **A structural guard can pass against reverted code.** A regex using
   `[\s\S]*?` matched an unrelated `neighbors:` fifteen lines further down the
   file, so the test stayed green with the fix removed. Bound the match
   (`[^)]*`), and **always run the revert** — that is the only thing that caught it.
3. **A Postgres test that reads ambient rows tests the environment.** The
   batch-resolution test read whatever was in `items`; it passed against seeded
   production and failed on CI, where the table is empty after a fresh
   migration. Seed your own rows and delete them in `t.after`.
4. **`/tmp/$(basename $f)` collides.** Backing up `lib/db/index.js`,
   `lib/search/index.js` and `lib/taste-graph/index.js` wrote all three to
   `/tmp/index.js.bak`; the restore put `lib/db` inside `lib/search`. Use unique
   names, or just `git checkout`.
5. **The MCP browser network log is cumulative across navigations.** It showed
   three `paris-roads.json` requests and nearly produced a false regression
   report. `performance.getEntriesByType('resource')` is page-scoped and honest.
6. **`git add -A` sweeps in `.impeccable/`** plugin scratch. Now gitignored.
7. **Read the migration header before calling something a bug.** Gamma's
   `contributors = 0` looked like a broken write path; `schema-v22` says in its
   own comments that it is deliberate. The consequence was still worth
   reporting — but as a product-state fact, not a defect.

Still in force from before: every `supabase/schema-vN-*.sql` must insert its
version into `app_schema_migrations`; never export `DATABASE_URL` globally when
running tests (use `TEST_DATABASE_URL`); never force oversized viewports on the
shared preview pane; a test can only catch a bug in the backend it runs against.
