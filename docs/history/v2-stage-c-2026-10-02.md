## Deploying ahead of the schema (v59, v60)

`stageCApplied()` (`lib/db/dm/core.js`) probes v59's columns once per
process; every DM reader falls back to the v48 shape and every Stage C act
refuses by name (`DM_SCHEMA` → "this is not available on the desk yet")
until the file is applied. The gift store probes `wardrobe_transfers` the
same way (`GiftRefused unapplied` → 503). `enqueueNotification` treats a
kind the applied CHECK does not know as `unapplied`, not a fault. Apply in
order: v56 (eBay feed, #479) → v57 → v58 (#480) → v59 → v60, each with the
file's VERIFY lines.

## Known integration limits

- No signed-in browser pass: the desk and the gift tab need an account identity, and the dev server reads production where v59/v60 are unapplied (every Stage C act would answer "not available yet"). The laws are proven at the store layer; the components compile and are built.
- Media: never exercised against a real bucket (gated off by owner decision).
- Wardrobe Cover Flow / Grid / List / detail / Size Engine estimate / Share: not in this stage.
- Push or email delivery of any notice: does not exist; everything is in-app.

## Recommendations that change founder intent

1. **Suppress the clear-history notice** (`DM_CLEAR_NOTICES=0`). Clearing one's own inbox is ordinarily private; the notice is built and ON as requested, the switch is one variable.
2. **Keep profile-shared notices aggregated by day** (built that way), rather than one instant alert per share — an instant alert lets the passenger infer who shared from timing.
3. **No archive storage tier** for DM images — it would cost more at these object sizes, not less.
